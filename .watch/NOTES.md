# Watcher notes, audit of the shipped amarel-vscode-setup skill

Audited 2026-08-21 against `.watch/GOAL.md`, on branch main at merged commit 7f1450e. Read-only on the repo except this file.

## Verdict

The runbook mirrors agree, the confirm-before-file rule is correctly gated on the user, and the routing description is wide enough that every phrase tested would plausibly load the skill. The one-click claim is where it breaks. `phase_compute_session()` in `scripts/setup.sh` is written as non-fatal throughout, so three separate early returns leave `amarel-dev` uninstalled and the login-node guard un-appended, and the setup then prints "Server-side setup complete" and tells the user to point their editor at `${AMAREL_HOST}`, which is a login node. That is goal 1 and goal 5 failing in the same code path. Below that, several connect-time refusals are neither maintenance windows nor recoverable without a manual command, and the session-length promise in the skill description ("give me a fresh 8 hour session") has no implementation behind it: `dev-session` takes no length argument and section 13.9 never tells the agent to edit the conf. Hard-coded owner values are all in comments or example output, not in code that runs.

## Checked and found clean

- **Routing, item 1.** Read the frontmatter `description` at `skills/amarel-vscode-setup/SKILL.md` lines 3 to 51. Per-phrase verdict: "it's not working" HIT (named verbatim), "amarel is broken" HIT ("something is broken"), "my vscode won't connect to the cluster" HIT ("it won't connect", "my editor can't reach amarel"), "I'm on a login node again" HIT ("I landed on a login node"), "how long is left on my job" HIT (named verbatim), "set up vscode on amarel" HIT (first line), "stop my job" HIT ("stop my amarel job", "cancel the job"), "the remote window is stuck" HIT by the catch-all only, see the LOW finding, "help my editor died" HIT ("help", "my amarel session died"). No phrase I tested looks like a miss.
- **Mirror contradictions, item 2.** Stripped the 51 frontmatter lines from SKILL.md and diffed the remainder against AGENTS.md in full. The diff is 72 lines and every changed line is in the first screen: AGENTS.md carries an agent-framework preamble and a "What this repo does" section, SKILL.md carries a Claude Code note and its own intro paragraph. From the "Execution contract" block onward the two files are byte-identical. No place where they give different instructions.
- **Confirm-before-file, item 6.** Both filing paths are gated on the user, not on the machine check. `AGENTS.md` line 2905 ("Step 3b, ask the user to confirm") states the machine check is necessary and not sufficient and says to wait for their answer. Line 2919 requires all three of fix applied, step 3 passed, user confirmed. The first-principles lane at line 3129 ("Step 5, file the issue, once they confirm") matches, and line 3125 says "Their confirmation is what counts." Both also require a duplicate search and `gh auth status` before `gh issue create`. Mirrored identically in SKILL.md.
- **Hard-coded owner values, item 4.** Grepped the repo excluding `.git`, `_salvaged-from-Downloads` and `cluster/VERIFICATION-*.md`. `gpuk012` appears only as example output in both runbooks (AGENTS.md line 397, SKILL.md line 422); `gpuk008` only in prose and in a measurement comment (AGENTS.md line 2792, SKILL.md line 2817, `cluster/amarel-dev-connect` line 27). No hard-coded node name, job number or `/Users/sj1136` path is used by any code that runs. `ADL_PARTITION` defaults to empty in `cluster/amarel-dev-lib` line 29 and is detected at setup with `sbatch --test-only`, never assumed. The 3-day walltime at `cluster/amarel-dev-lib` line 32 and `scripts/setup.sh` line 992 is a fallback default, and `setup.sh` lines 1071 to 1114 do ask the user, so setup itself satisfies goal 4. The gap is afterwards, recorded as a MEDIUM above.
- **User-facing leakage, item 5.** Grepped `README.md` and `docs/index.md`, `docs/README.md`, `docs/source-control-git-fix.md` for untested-item lists, verification status and dev-mode text. Nothing found. `README.md` mentions "Phase 13" twice (lines 224 and 255) as a plain pointer, which is a phase label, not an internals dump. The dev-mode section and the untested-items table live in AGENTS.md and SKILL.md, which are exempt. `cluster/VERIFICATION-2026-08-21.md` sits in `cluster/`, not `docs/`, and is not linked from README.md.
- **Login-node landing at connect time.** `cluster/amarel-dev-connect` resolves the node from `squeue` and never falls back to the login node. If no node resolves it fails rather than connecting. The ssh_config `amarel-jump` block carries an explicit "DO NOT POINT YOUR EDITOR AT THIS ENTRY" comment (`scripts/setup.sh` lines 1215 to 1222), and the `.bash_profile` guard refuses an editor bootstrap on a host whose short name begins with `amarel`, which I confirmed live is `amarel3`.
- **Remote shell noise gate.** Ran `ssh -o BatchMode=yes amarel-jump true` and confirmed stdout is empty on this account. The post-quantum warning banner the server prints goes to stderr, so it does not trip the Phase 9.6 gate or ride the tunnel.
